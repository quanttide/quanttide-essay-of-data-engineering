# 从模糊判断到可复现证据：数据智能体的四层形式化工程方法论

**工作论文 v0.1**  
**作者**：量潮数据工程团队（待补充）  
**日期**：2026-10-09  
**关键词**：数据智能体；形式化验证；数据工程；可复现性；可证伪性；搜索行为诊断；四层框架

---

## 摘要

市场数据智能体通常将用户问题直接映射为意图识别、指标生成、SQL/代码与答案，擅长查询执行，却缺少将模糊判断形式化并验证的环节。本文提出一种四层方法论：**数据需求 → 数据意图 → 数据规格 → 数据实现**。其中，数据需求是价值合同；数据意图是形式化验证合同，负责把模糊意图转为形式化对象、操作定义、指标、可证伪命题、因果图、验证方法与验证结论；数据规格是约束合同，是数据意图的具象与计算机实现的约束；数据实现是工程合同，负责用具体语言、管道、命令执行。以“量潮搜索工程”诊断多智能体搜索低效为例，本文展示四层如何把“搜索效率低”转成可追溯、可证伪、可复现的数据产物。该方法论的核心区别在于：数据智能体不再是查询执行器，而是形式化验证器。

---

## 1 引言

数据智能体的常见链路是：

> 用户问题 → 意图识别 / 槽位填充 → 规格 / 指标 → SQL / 代码 → 答案

这条链路擅长“查数”，但存在结构性缺陷：它把“意图”理解为任务意图，即“你要查什么”，而不是“你的判断如何被严格表达并验证”。结果是，指标算得很准，概念却可能是错的；相关性被当成因果；结论不可复现、不可争论、不可追溯。

本文概括我们提出的一种四层形式化工程方法论：

> **数据需求 → 数据意图 → 数据规格 → 数据实现**

其核心主张是：

- **数据需求**：价值合同，回答“为什么做、为谁做、什么算成功”。
- **数据意图**：形式化验证合同，回答“意图如何被严格表达、怎么定义、怎么证、验了什么”。
- **数据规格**：约束合同，是数据意图的具象，也是计算机实现的约束。
- **数据实现**：工程合同，回答“用什么语言、什么管道、什么命令跑出来”。

本文以“量潮搜索工程”为例，说明该方法论如何把“搜索效率低”这类模糊判断，转成可追溯、可证伪、可复现的数据产物。

## 2 问题陈述

在数据工程与数据智能体实践中，模糊判断普遍存在。例如：

> “多个智能体的搜索行为不稳定，经常出现乱七八糟的情况。”

市场数据智能体通常直接将其转为查询：搜索次数、空结果率、重复查询率、平均耗时。然后给出建议：减少搜索、改提示词、加预算。这种做法的问题不在 SQL 能力，而在缺少形式化验证：

1. **概念未澄清**：搜索行为是什么？“乱”相对于什么规范？
2. **指标未合法化**：搜索次数多一定是低效吗？探索性检索是否应计入？
3. **命题未形式化**：哪些是相关命题？哪些是因果命题？可证伪条件是什么？
4. **验证未执行**：只描述统计，不做假设检验、效应量、置信区间与因果识别。
5. **流程不可追溯**：报告结论无法回指到具体指标、命题与数据产物。

因此，问题不是“如何把问题翻译成 SQL”，而是“如何把模糊判断转成形式化验证，并进一步转成可复现的工程产物”。

## 3 方法论：四层形式化数据工程框架

### 3.1 总览

| 层级 | 合同性质 | 核心问题 | 主要输出 |
|:--|:--|:--|:--|
| 数据需求 | 价值合同 | 为什么做？为谁做？什么算成功？ | 痛点、目标、成功指标、范围、非目标、利益相关者、约束 |
| 数据意图 | 形式化验证合同 | 意图如何严格表达？怎么定义、怎么证、验了什么？ | 形式化对象、操作定义、指标、命题、因果图、约束、验证方法、验证结论、验收清单 |
| 数据规格 | 约束合同 | 形式化怎么具象？计算机实现要遵守什么？ | 数据源、采集规则、清洗流程、表结构、指标计算口径、流程步骤、质量校验、追溯矩阵 |
| 数据实现 | 工程合同 | 用什么语言、什么管道、什么命令跑出来？ | 技术栈、数据管道、命令行入口、质量校验脚本、版本管理、执行验证、报告生成 |

一句话：

> **需求是价值合同，数据意图是形式化验证合同，数据规格是约束合同，数据实现是工程合同。**

层间关系为：

> **数据需求 → 数据意图 → 数据规格 → 数据实现**

其中：

> **数据意图 = 形式化验证。**  
> **数据规格 = 数据意图的具象 + 计算机实现的约束。**  
> **数据实现 = 具体工程。**

可追溯 ID 建议为：

> `REQ-001 → INT-001 → SPEC-001 → IMP-001`

任何一层都可以反向挑战上一层。数据意图可以挑战数据需求；数据规格可以暴露数据意图不可计算；数据实现可以修正数据规格。

---

### 3.2 数据需求：价值合同

数据需求层回答“为什么做”。它写：

- 背景与痛点；
- 目标与非目标；
- 成功指标（业务口径）；
- 范围；
- 利益相关者；
- 约束。

它不写：

- 形式化对象；
- 指标公式；
- 表结构；
- 代码与工具。

成功指标必须是业务后果，而不是交付物。“产出报告”不是成功指标；“搜索相关失败率下降”“任务成功率提升”才是。

---

### 3.3 数据意图：形式化验证合同

数据意图层是本方法论与市场数据智能体最本质的区别。它不是任务意图识别，也不是槽位填充，而是**形式化验证**。

它写：

- **形式化对象**：会话、轨迹、动作、搜索事件、查询、结果、变量、随机变量。
- **操作定义**：搜索判定、查询漂移、结果被消费、结果未利用、过度搜索、有效命中率。
- **指标**：空结果率、错误率、结构化结果占比、结果体量、过载率、连续搜索率、重复查询率、搜索后读文件率、延迟中位数。
- **命题与假设**：H1–H3 的形式化表述与可证伪条件。
- **因果图**：变量之间的因果假设与混杂变量。
- **约束与不变量**：搜索次数 ≤ 工具预算；查询与任务目标相似度 ≥ δ；结果引用覆盖 ≥ γ。
- **验证方法**：零假设/备择假设、统计检验、效应量、置信区间、样本量、偏差控制、因果识别。
- **验证结论**：对 H1–H3 的实际检验结果，含统计量、p 值、效应量、置信区间；相关与因果分列。
- **验收清单**：每个指标可复算；每个命题有检验结果；未识别的不得冒称因果；报告结论可回指。

这一层回答：

> **意图如何被严格表达？怎么定义？怎么证？验了什么？**

---

### 3.4 数据规格：约束合同

数据规格层是数据意图的具象，也是计算机实现的约束。它不写具体语言与工具，而写：

- **数据源与采集规则**：来源、路径、格式、导出方式、只读约束、失败隔离。
- **清洗流程与归一化规则**：会话元数据、消息列表、工具调用、结果文本的统一形状。
- **表结构**：`sessions`、`messages`、`tool_calls`、`search_events` 等表的字段与类型。
- **指标计算口径**：分母、阈值、聚合维度（全局、按来源、按会话）。
- **流程步骤**：采集、清洗、分析、验证、报告，每步的输入、处理规则、产物、验收标准。
- **质量校验**：manifest 行数核对、四表行数核对、报告与 JSON 数值一致。
- **追溯矩阵**：业务成功指标 ← 规格指标 ← 命题 ← 报告章节。

一句话：

> **数据规格把“形式化验证”翻译成“计算机实现必须遵守的约束”。**

---

### 3.5 数据实现：工程合同

数据实现层只写具体工程：

- 技术栈：Python、polars、Parquet。
- 数据管道实现。
- 命令行入口：`load`、`clean`、`analyze`、`verify`。
- 质量校验脚本。
- 版本管理：数据、代码、报告各自版本与时间戳。
- 执行验证并产出检验结果。
- 报告生成。

它不重新定义指标，不重新解释概念，不另立流程。所有定义来自数据意图，所有约束来自数据规格。

## 4 案例：量潮搜索工程

### 4.1 数据需求

多个智能体（pi、zed、hermes、hermes-backup、dsh、opencode）搜索行为不稳定，影响任务成功率与使用者信任。目标：定位搜索低效主因，形成可验证的改进方向。成功指标：搜索相关失败率下降、任务成功率提升、低效会话占比下降、结果采纳率提升。范围：近三个月若干智能体会话。非目标：不重写检索算法。

### 4.2 数据意图

搜索被形式化为任务目标、信息需求、工具预算与反馈信号下的决策过程。操作定义包括搜索判定、查询漂移、结果被消费、结果未利用、过度搜索、有效命中率。指标包括空结果率、错误率、结构化结果占比、结果体量、过载率、连续搜索率、搜完又搜未行动率、会话内重复查询率、搜索后读文件率、延迟中位数。命题 H1：空结果率高的会话更易失败；H2：连续搜索与结果未被消费正相关；H3：结果过载与有效命中率负相关。因果图：`prompt_version → query_drift → result_unused → task_fail`。验证方法：两比例 z 检验、Spearman、卡方、效应量、置信区间、分层控制、A/B 或反事实。

### 4.3 数据规格

数据源为 6 个智能体的本地会话数据。采集规则：只读复制或导出为 JSONL，写入 `data/raw/<来源>/`，写 `manifest.json`。清洗后产出四张 Parquet 表：`sessions`、`messages`、`tool_calls`、`search_events`。流程五步：采集、清洗、分析、验证、报告，每步固定输入、处理规则、产物与验收。质量校验：行数核对、搜索计数核对、报告与 JSON 数值一致。追溯矩阵：业务指标 ← 规格指标 ← 命题 ← 报告章节。

### 4.4 数据实现

技术栈：Python + polars + Parquet。命令行入口：`load`、`clean`、`analyze`、`verify`。执行验证：对 H1–H3 计算统计量、效应量与置信区间；可行时做因果识别，不可识别则只报相关。报告固定章节：总览、按来源、结果质量、结果体量、行为模式、搜索后首个动作分布、每会话摘要、诊断与证据强度。报告结论必须回指到具体指标与命题，不得由模型自由生成。

## 5 与现有数据智能体对比

| 维度 | 市场数据智能体 | 本方法论 |
|:--|:--|:--|
| 意图 | 任务意图、槽位填充 | 数据意图、形式化验证 |
| 核心动作 | 识别需求，生成查询 | 形式化对象，定义指标，登记命题，执行验证 |
| 输出 | 答案、图表、报告 | 形式化定义 + 验证结论 + 证据链 + 工程产物 |
| 验证 | 结果对不对 | 概念是否合法、指标是否有效、命题是否可证伪 |
| 失败模式 | 答非所问、指标漂移 | 范畴错误、本体错位、概念混淆 |
| 与用户关系 | 执行者 | 研究伙伴、形式化验证者 |
| 可追溯性 | 需求 → 查询 | 需求 → 意图 → 规格 → 实现全链追溯 |

一句话：

> **市场数据智能体是查询执行器；本方法论的数据智能体是形式化验证器。**

---

## 6 贡献与创新

1. **把数据意图升级为形式化验证层**：不再把意图理解为“查什么”，而是“如何严格表达并验证”。
2. **把数据规格定义为约束合同**：数据规格是数据意图的具象，也是计算机实现的约束，而非简单字段清单。
3. **建立全链追溯**：业务成功指标 ← 规格指标 ← 命题 ← 报告章节，逐列可回指。
4. **可证伪与验证结论并置**：每个命题有可证伪条件、检验统计量、p 值、效应量与置信区间。
5. **工程可复现**：固定流程步骤、输入输出、质量校验、版本管理与命令行入口，换一台机器也能重跑。
6. **区分相关与因果**：未识别的不得冒称因果；可行时用 A/B 或反事实做因果识别。

---

## 7 局限与未来工作

**局限**：

- 因果识别依赖 A/B 或反事实，离线诊断中常不可得。
- 任务成功与结果消费可能使用代理指标，存在测量误差。
- 人工标注成本高，跨来源归一化复杂。
- 当前验证尚未完全自动化，`verify` 步骤需按验证方法执行。

**未来工作**：

- 自动化形式化验证：从数据意图自动生成检验代码与验收报告。
- 在线监控：把离线诊断转为持续监控与告警。
- 跨案例泛化：在更多数据工程案例中验证四层框架。
- LLM 辅助假设生成与检验，但结论仍须回指指标与命题。

---

## 8 结论

本文概括了一种四层形式化数据工程方法论：

> **数据需求 → 数据意图 → 数据规格 → 数据实现**

数据需求是价值合同；数据意图是形式化验证合同；数据规格是约束合同，是数据意图的具象与计算机实现的约束；数据实现是工程合同。以量潮搜索工程为例，该方法论把“搜索效率低”转成可追溯、可证伪、可复现的数据产物。

其核心区别在于：

> **数据智能体不再是查询执行器，而是形式化验证器。**

不是查数，是建构可验证的认知。  
不是给答案，是给一条可检验的认知链。
